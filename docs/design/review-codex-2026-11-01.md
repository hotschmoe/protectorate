# Adversarial review: Codex, 2026-11-01

Read-only run of `codex exec -s read-only` over SPEC.md, docs/design/ and the session doc. Accepted fixes are in SPEC.md section 12a.

## Findings, ranked by severity

1. **High — A resleeve can start a new harness while the old one still writes to the workspace.** [Sleeves §2.d, Quiescing → Capturing → Launching](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:539>) sends `StopIncarnation` and immediately proceeds to checkpoint, brief, and launch. It never waits for the old process tree to be confirmed dead, contradicting invariant I5 in [§2.a](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:345>). A slow or unresponsive harness can edit files during capture or alongside its replacement. **Fix:** make confirmed scope death, with a kill and probe timeout, a required transition before checkpoint or launch.

2. **High — An absent scope does not prove an incarnation never started.** [Sleeves §2.c, `StartIncarnation` probe](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:456>) calls an absent scope `NotApplied`. After a crash, the harness may have started, run tools, and exited before the probe. Retrying its start can repeat work or resume a session whose effects were never recorded. **Fix:** distinguish “never started” from “started and now gone” using a durable launch receipt and process or session evidence; treat ambiguous cases as uncertain.

3. **High — A rejected prompt leaves activity stuck in `Working`.** [Sleeves §2.b–c](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:360>) moves `Idle → Working` when `SendPrompt` is emitted. The effect table permits a definitive `Nack → Rejected`, but the activity table has no rejection transition. No turn exists to settle, so later queued work waits until a silence guardrail fires. **Fix:** tie activity to effect resolution; on definitive rejection, return to Idle, report the failure, and deliver the next queued item.

4. **High — Approval probes mistake “no longer pending” for “our answer was applied.”** [Sleeves §2.c, `RespondApproval`](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:456>) treats a vanished approval as Applied. It could instead have disappeared because the harness timed out, the turn ended, or another client answered it. The hub would report its decision as confirmed without evidence. **Fix:** require a native response ID or matching decision in harness state; otherwise retain `Uncertain`.

5. **High — The one-way trust claim is false at the network boundary.** [SPEC §2 principle 4](</home/hotschmoe/github/protectorate-next/SPEC.md:32>) says nodes “never initiate anything toward the hub.” [Network §4.4](</home/hotschmoe/github/protectorate-next/docs/design/network-trust-language.md:275>) explicitly requires node-initiated control, DERP, disco, and netmap traffic into hub-hosted processes; [§4.5](</home/hotschmoe/github/protectorate-next/docs/design/network-trust-language.md:304>) also admits nodes can reach the Traefik API router on the LAN. A hostile node can send traffic to these hub surfaces even if tailnet ACLs block new node-to-hub application flows. **Fix:** state the narrower property precisely, isolate the exposed processes, and enforce source separation at Traefik and the host firewall now rather than leaving the agent VLAN for later.

6. **High — Node job “unknown” can mean a completed job whose record expired.** [Sleeves §2.e](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:607>) resubmits the same attempt when `Status` says “unknown job.” [Nodes §1.3](</home/hotschmoe/github/protectorate-next/docs/design/nodes-ci-deliverables-verus.md:157>) retains completed jobs for only one hour and caps records at 4096. A partition or busy node can outlast either limit; the hub then interprets a completed job as never submitted and runs it again. **Fix:** keep durable job tombstones beyond the hub’s uncertainty and recovery window, or make `unknown` ambiguous and require a new explicit attempt.

7. **High — The trust check at enrollment does not establish a lasting control-key pin.** [Network §5 step 5 and §6](</home/hotschmoe/github/protectorate-next/docs/design/network-trust-language.md:339>) compares the QR fingerprint with the hub’s key, which detects a forged key *at approval*. The report also says `tsnet` fetches `/key` itself and that the proposed re-check is “not airtight” ([§6](</home/hotschmoe/github/protectorate-next/docs/design/network-trust-language.md:424>)). A compromised Traefik endpoint after enrollment may present a different control key to a restarting node. **Fix:** enforce the pin in the component that performs the actual control connection, fail closed on mismatch, and test key rotation and restart behavior.

8. **High — Executing the installer precedes verification of what it does.** [Network §5](</home/hotschmoe/github/protectorate-next/docs/design/network-trust-language.md:319>) pipes a remotely fetched script to `sh`; [Nodes §5](</home/hotschmoe/github/protectorate-next/docs/design/nodes-ci-deliverables-verus.md:344>) signs the binary checksums, not the script being executed. A compromised script can run commands or replace the embedded verification key before any checksum check. A tag in the URL does not make GitHub raw content immutable. **Fix:** sign and verify the installer before execution, or use a tiny, independently pinned bootstrap command that verifies the release manifest and script.

9. **High — A compromised sleeve has access beyond its workspace despite the “light isolation” description.** [Sleeves §1.4](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:95>) bind-mounts the host root read-only, shares the host network, and makes the owner’s download caches writable; [Nodes §2](</home/hotschmoe/github/protectorate-next/docs/design/nodes-ci-deliverables-verus.md:185>) gives sleeves a GitHub PAT. Masks cover a named set of secret locations, so an agent or tool can read other unmasked host files, reach LAN services, poison shared caches, and use or leak the PAT. This is acknowledged as non-hostile isolation, but the blast radius is material for vendor CLIs and node-sourced prompt injection. **Fix:** define the acceptable threat model explicitly; use allowlisted mounts, private or verified caches, restricted network egress, and a narrower GitHub credential where hostile code is in scope.

10. **Medium — Several persisted states have no specified crash recovery action.** [Sleeves §1.10 and §2.c–e](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:274>) replay the journal, but recovery rows cover `Intent` and `Sent`, not `Probing`; the job table does not say how `Collecting` or `Cancelling` restarts its I/O. A hub crash after entering one of those states can restore the label without restarting its probe, artifact fetch, or cancel request. **Fix:** define a recovery action for every nonterminal state and fuzz crash insertion at every journal boundary.

11. **Medium — Cancellation can remain stuck indefinitely.** [Sleeves §2.e, `Cancelling`](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:620>) reaches `Cancelled` only on a status response. There is no unreachable, timeout, expired-record, or node-restart transition. A disconnected node leaves the job in `Cancelling` forever, even when its process has died. **Fix:** add a bounded cancellation reconciliation path with `Lost` or `Uncertain` and a terminal outcome backed by evidence.

12. **Medium — Root stop during provisioning can leave an unmanaged worktree.** [Sleeves §2.a](</home/hotschmoe/github/protectorate-next/docs/design/sleeves-state-machines.md:299>) allows `Stop` from `Provisioning`, but `ProvisionDone` is only handled while still Provisioning. If `git worktree add` finishes after Stop, its completion is stale, and no cleanup or accounting transition is specified. **Fix:** make provisioning cancellable with an explicit completion barrier and cleanup, or wait for it to finish before `Stopped`.

13. **Medium — The proposed CI status trusts an untrusted node’s claim.** [Nodes §2](</home/hotschmoe/github/protectorate-next/docs/design/nodes-ci-deliverables-verus.md:209>) posts a GitHub commit status from a node job result. [Network §4.4](</home/hotschmoe/github/protectorate-next/docs/design/network-trust-language.md:301>) correctly says a node can lie. Artifact hashes and bounded frames verify transfer integrity, not that `make test` ran or passed. A compromised node can return exit 0 and a fabricated log, yielding a green status. **Fix:** label node results as attestations from that node, restrict release gates to trusted or independently replicated builders, and avoid claiming verification from transport checks.

14. **Medium — The Verus safety rule is changed without owner approval.** The owner’s [rule 6](</home/hotschmoe/github/protectorate-next/docs/sessions/2026-11-01-redesign.md:16>) says unsafe code is allowed only where Verus proves bounds. [SPEC §10](</home/hotschmoe/github/protectorate-next/SPEC.md:295>) says those rules apply “as written” but exempts OS FFI crates, following [Nodes §6](</home/hotschmoe/github/protectorate-next/docs/design/nodes-ci-deliverables-verus.md:465>). That is a substantive exception to an explicit constraint, even if FFI may make it necessary. **Fix:** present the exception as a deviation requiring the owner’s decision, or choose an implementation that meets the stated rule.

15. **Low — The “two binaries” goal counts release artifacts, not runtime executables.** [SPEC §§2, 3.2, 3.4, 6](</home/hotschmoe/github/protectorate-next/SPEC.md:24>) promises two binaries plus Flutter, while the hub embeds and executes headscale and `member`, nodes execute `member`, and the Pi Durable experiment adds Node and a bridge. The release may have two *named native artifacts*, but installation, supervision, updates, and failure modes still involve more executables. **Fix:** track both deliverable count and runtime executable/dependency count, and make each added runtime an explicit acceptance decision.
