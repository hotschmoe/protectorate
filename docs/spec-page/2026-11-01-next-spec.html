PROTECTORATE / NEXT

A self-hosted software factory on one hub machine. You, Envoy and vendor general agents dispatch coding work to sleeves. A sleeve is an untouched vendor CLI or Pi, bound to one directory in a light sandbox. The hub also reaches untrusted nodes to inventory them, maintain them and run builds and tests on other architectures. Nodes never reach back.

Principles9 RULES

DeterministicIf code can decide it, code decides it: dispatch, quota ranking, retries, guardrails, resleeves, scheduling, briefs. An LLM only judges.
Hands-offHarnesses run through their TUI or official headless protocol, with their own config and auth. No wrappers, patches, hooks or typed keystrokes.
One writerOne core task owns all state. Every event goes through apply(state, event), is journaled, then executed.
Untrusted devicesThe hub reaches into nodes. Nodes never start application traffic to the hub; their only outbound traffic is control and DERP to the sandboxed headscale. Their bytes are parsed as hostile, and their job results are claims, not proof.
Record firstEvery write to a harness or node is an fsynced effect record before its first byte leaves. An unconfirmed write is Uncertain, never blindly retried.
Fewest partsTwo binaries plus the Flutter apps. A new dependency needs a reason that code cannot meet.
LAN onlyprotectorate.hotschmoe.com answers on the LAN and the owner's WireGuard only. WAN access is a separate, later design.
Repo rulesNo emojis, full migrations, real-binary e2e and fuzz tests only, no hand-edited generated code.
Verus, narrowProofs only where bytes come from outside or offsets are computed, and nothing else to compare against.

System map3 PLANES

Clients come in through Traefik. The hub owns everything. Nodes get dialed and never dial back. The only thing a node may reach is the control plane.

Headscale, official and unmodified

Built from upstream in CI at a pinned tag (v0.29.7 today). The hub binary embeds it and runs it as a sandboxed child from a sealed memfd. It is inside the hub binary, but not the hub process, because Serve takes over signals and calls log.Fatal. Admin goes through its own CLI over a unix socket. No API key ever exists.

Go is two mains in one module

go/cmd/headscale is upstream's main. go/cmd/member is about 500 lines of tsnet glue: userspace, no TUN, no root, no tailscaled. Both are built with CGO_ENABLED=0. The rest is Rust, plus Dart for Flutter. Zig is only the C toolchain behind cargo-zigbuild.

One-way trust7 LAYERS

"Nodes can't send to the hub" holds at the policy, the packet filter, the listener and the credential. One surface is irreducible: nodes must talk to headscale. So headscale holds none of the hub's secrets.

Layers

  1. One policy rule, tag:hub -> tag:node:7475, in a static embedded file. Nodes cannot request tags.
  2. The hub's own packet filter drops node-initiated SYNs and UDP.
  3. The hub member has no tailnet listener, and peerAPI is compiled out.
  4. The hub API binds loopback and the proxy listener only, and the listener check refuses 100.64.0.0/10.
  5. Nodes hold nothing the hub accepts.
  6. The control plane runs as a separate sandboxed process.
  7. Node output is hostile input: framed, capped, Verus-checked.

What a hostile node can still send

  • Control and DERP traffic to headscale. A headscale compromise means control of the nodes, but not of the hub's state or tokens.
  • Answers to hub requests, parsed by the frame codec under Verus.
  • Non-SYN TCP, ICMP and TSMP packets that reach a netstack with nothing listening.
  • On the LAN without an agent VLAN, the same front door as any host: static files and 401s.

A machine can be a node and also host a client. Those are two unrelated identities: the node key lives in the service state dir, and the client token lives in the user's 0600 config.

Scan to join8 STEPS

The new machine shows a QR code, your phone approves, and the hub does the rest through headscale's own CLI. Nothing on the node ever calls a hub endpoint.

Alternatives rejected: a code shown on the phone and typed on the node would need an unauthenticated node-to-hub endpoint. A pre-auth key in the one-liner is a bearer secret in shell history. SSH bootstrap would mean the hub holds SSH credentials for every machine.

Light isolation: keep

  • user, mount, PID, IPC and UTS namespaces
  • host root read-only; workspace and private home writable

  • a systemd scope per incarnation with limits, cgroup.kill and the reaper

Light isolation: cut

  • the network namespace and egress proxy (security, not stomp prevention)
  • cache overlays (bind the shared download caches instead)
  • nested cgroup delegation and the pin-approval gate
  • about 4.8k lines down to 1.2k

Panes

  • the hub owns every PTY; tmux goes
  • a byte ring with offsets, re-attachable from any client
  • status from herdr-style screen rules, never hooks; no match means Unknown
  • the hub never types into a pane after launch
  • updates re-exec in place and keep the pane fds

State machines5 MACHINES, 1 WRITER

Every machine is a pure apply(state, event) with a fuzz target. The fuzz target compares it against a table-driven reference model and checks that replaying the journal equals the live state. Every observation carries g or attempt, and anything stale is dropped.

Sleeve lifecycle

Invariants: at most one incarnation is not known dead, and g+1 starts only after g is confirmed dead or never started. g only grows. Claims never overlap. A stopped parent has no live child.

Activity of the current incarnation

After review, a Delivering{id} state sits between Idle and Working while a queued prompt is in flight. Headless sleeves read the protocol; panes use debounced screen rules. DONE is Idle not yet seen. Send takes a mode, steer or queue, with no silent downgrade. The queue lives on the sleeve, so it survives resleeves.

Effect record: every write to a harness or node

Any open record becomes Fenced when its target's g advances, and the brief lists it as "may have been applied". An unsafe send to a vendor CLI never goes back from Uncertain to Intent; only you or a guardrail can abandon it. A client retry with the same request_id gets the same record.

Guardrail trip, then resleeve

Planned and forced resleeves share one path through Capturing, which builds the brief. Before resleeving, a crash resumes the same harness up to twice in 10 minutes, and a loop or silence interrupts first. Targets come from the sleeve's ordered resleeve_to list, skipping unhealthy, excluded or quota-short ones. A third resleeve within an hour parks the sleeve.

Node job: the hub asks, the node only answers

The node journals (job, attempt, digest) before exec and treats an equal resubmit as a no-op. A job never re-runs by itself. A node that comes back from Lost reports what it knows, and an answer for an older attempt is dropped.

Code decides

  • dispatch by quota at spawn and guardrail time: select_target(task_size, allow, mode, exclude, quota, health)
  • retries, probes, idempotency, steer and queue rules
  • every guardrail, resleeve, target choice and flap limit
  • mail delivery, cascades, budgets, approval timeouts
  • node scheduling, job submit, poll and collect, brief facts

Envoy decides

  • goal decomposition and briefs
  • repo, workspace and whether to use children
  • the task-size estimate fed to dispatch
  • reading reports: accept, rework or escalate; reviewing diffs
  • which backlog item spare quota goes to

Envoy never ranks harnesses, retries or runs a guardrail resleeve. Code never resleeves a healthy idle sleeve to chase quota, which would bust its prompt cache.

History and continuation3 TIERS

Handoff and forced resleeve are the same flow. Code builds a brief from facts in under a second. Only a planned resleeve waits for an LLM summary, because a crash has no time to.

Tier 1, cheapest

Native resume

The session still exists and the same harness is wanted. Relaunch with the official resume flag. No brief, no model.

Tier 2, every other case

Continuation brief

Built by code in .protectorate/BRIEF.md: the task, where it stopped, git state, files touched, tests, open items, effects that may have been applied, and pre-run search hits. Planned resleeves add an LLM summary.

Tier 3, on demand

Search

protectorate history search | read over a keyword index of every native log. The brief already carries the top hits, because pi_local is the weakest reader.

Storage

  • one SQLite file through rusqlite (bundled, FTS5): sessions, cursors, turns, chunks
  • derived and rebuildable; native logs stay authoritative and are only read
  • a framed tail reader per log, with the cursor written in the same transaction
  • vectors off until keyword search falls short; then a llama.cpp server over HTTP, with brute-force cosine in Rust

What mainplane actually does

No index, no vectors, no compaction. At the context limit it fails the session. /continue starts a new one told to "retrieve key context from it as you go", and the agent runs rg over the old log. That works because mainplane owns the loop and runs frontier models. We take the shape as the future compaction replacement: end the session, then continue with a brief.

NodesSHARED / CARE

One node binary per OS. It is inventoried every 10 minutes and sampled every 15 to 60 seconds, all on hub-initiated calls. Jobs run sandboxed, capped and journaled, and never re-run by themselves.

Care machines are never scheduled, but they still get owner-granted maintenance jobs, refused while someone is at the keyboard. Presence is reported as PRESENT, AWAY or UNKNOWN, with idle time, lock state and the source used. UNKNOWN counts as present on care machines and away on shared ones. Jobs default to 1 hour and 64 MiB of log. Output comes back as length-prefixed frames, never trusted as text. The old fleet's upkeep came from five causes: its own CA, address reports, firewall rules, the Windows logon task and uninstall ordering. Each one is gone in this design.

Git and CI

GitHub stays the origin. Only the hub holds the push token: a sleeve asks it to push its own branch with protectorate git push. The hub keeps bare mirrors as backup. Cross-arch CI is a hub rule: dispatch make test as a node job to each arch. Plain binaries; containers only on request. No Forgejo, GitLab or Woodpecker.

CLI and MCP

Both are generated from the proto, so MCP costs no hand-written code. The CLI is for shells and Envoy. MCP gives typed schemas, validated arguments and hints, and works for clients with no shell. Vendor general agents use remote MCP with an agent token. What each vendor app supports is unverified, so nothing depends on it.

Doctor

Checks harness CLIs and versions, credentials through the read-only quota readers (never printed), gh auth, sandbox prerequisites, disk and clock. Results are cached in doctor.json and feed dispatch and resleeve eligibility. Failures mail you.

Updates and moving the hubGITHUB RELEASES

Hub and nodes both update straight from GitHub releases, and the hub triggers the nodes. Moving the hub to another machine is a restore of the same backup that recovers a dead one.

Hub update

  1. Download the release and verify SHA256SUMS.sig with the key built into the running binary.
  2. Snapshot headscale's database, because its migrations are one-way.
  3. Re-exec in place, so sleeves keep running.
  4. If the health check fails within 2 minutes, a supervisor switches back to the previous release.

Node update, triggered by the hub

  1. The hub sends Update(version) over its own connection.
  2. The node fetches the release from GitHub itself, verifies it, stages it, and keeps the previous binary.
  3. The node restarts through its service manager.
  4. If the hub hasn't contacted it within 10 minutes, the node rolls itself back.

Order: hub first, then a canary node per OS and arch, then the rest. A node with no internet gets the bytes streamed over a hub-opened connection.

Moving the hub

  1. hub export: quiesce sleeves at a turn boundary, stop headscale, write a .pbackup, and push unpushed branches. The old hub writes a tombstone and never starts headscale again.
  2. Install the hub on the new machine and run hub import. The architecture may differ.
  3. Point Traefik's routes and the firewall rule at the new address. Nodes keep working with no re-enrollment, because the noise key and the hub member key moved.
  4. Sleeves come back through native resume or a brief. doctor flags any login that needs redoing.

Verus scope3 PHASES

Proofs go where bytes come from outside or offsets are computed, and nothing else exists to compare against. Verus is phased, so its cost is measured before it spreads. The state machines are excluded, because their tables are a perfect reference.

Shape

  • specs in cfg_attr(verus_keep_ghost, verus_spec(..)); vstd is an optional feature, so plain cargo needs no Verus
  • verify.sh runs a pinned release at --rlimit 20, then again at 10 to flag fragile proofs
  • overflow-checks = true in release for parser and writer crates
  • differential fuzzing against a second implementation

Excluded

  • state machines, guardrails and dispatch (reference model plus fuzzing)
  • per-harness JSON extractors (differential fuzzing against real logs)
  • Flutter, RPC handlers, glue, headscale
  • unsafe forbidden except Verus-proved helpers and the exempted OS FFI crates (D19)

Build orderSTAGES 0-6

  1. Network spike, throwaway. Prove headscale through Traefik, member on Windows, Linux and Android, and that the one-rule policy blocks a node-initiated flow. It runs first because it is the least proven part.
  2. Core. Workspace skeleton, proto, journal codec, core::apply for lifecycle, activity and effects, and the sleeve_core fuzz target with its reference model. No harness yet.
  3. Panes and one harness. Hub-owned PTYs, attach over WebSocket, screen rules, the headless Claude driver on the effect record, and the Flutter shell in the new look.
  4. Resleeve. Guardrails, the history index, the continuation brief, pi_local, and forced resleeve end to end.
  5. Network. The go/ module, embedded headscale and member, Traefik routes, scan to join, inventory and presence.
  6. Jobs. Node jobs, cross-arch CI, doctor.
  7. Hardening. The first Verus modules, remote MCP with agent tokens and the remaining harnesses.
