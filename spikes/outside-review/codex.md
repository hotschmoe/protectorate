The architecture says “lightweight,” but its first version combines a generated RPC stack, a self-hosted tailnet, five-platform node agents, container runtimes, a Flutter app, shared credentials, and an AI orchestrator. That is too much infrastructure before the core workflows have proved useful. [PROBLEMS.md](/home/hotschmoe/github/protectorate/PROBLEMS.md) already gives a better build order than [ARCHITECTURE.md](/home/hotschmoe/github/protectorate/ARCHITECTURE.md).

**What I would cut or defer**

- **Connect-RPC:** Use a small, versioned HTTP JSON API for the hub and WebSocket only for terminals. A CLI command need not map one-to-one to an RPC method; some commands compose several operations. Proto generation, committed clients, and server streaming add maintenance before there is a demonstrated interoperability problem. Keep machine-readable CLI output and explicit error codes.
- **tsnet + Headscale:** Defer both. You already have WireGuard for phone-to-office access. Plain WireGuard is the next step if more devices need reachability; it has fewer moving parts than running Headscale and embedding a tailnet in every binary. For hub-to-node work, **SSH-only is viable now**: the repo’s [spike](/home/hotschmoe/github/protectorate/spikes/ssh-agentless/README.md) measured 45 ms per multiplexed call and shows JSON over a persistent SSH session. Its real limitation is reachability of roaming nodes, not throughput. Add an overlay only for nodes SSH cannot reach.
- **Sleeves:** Keep tmux and Git worktrees as the default. For the specific PID-clobbering problem, use a PID namespace and cgroup on Linux when needed; a container is reasonable where toolchain packaging or stronger filesystem separation pays for it. Do not build a runtime abstraction or microVM implementation yet. MicroVMs are a later choice for genuinely untrusted work. Also, PID namespaces do not protect other agents if a sleeve can SSH back into the host with admin rights; credential scope matters more than the runtime label.
- **Hub binary versus container:** Keep the host binary. Managing tmux, SSH, credentials, and host resources from a container recreates the archive’s Docker socket and host-mount problems. Run it under a dedicated service account with narrowly granted privileges.
- **Go + Flutter versus all-Rust:** Go for the hub and CLI is a sound, small implementation choice. All-Rust does not eliminate the mobile UI problem and would make it harder to reuse mature phone terminal components. But **defer Flutter**, too: first prove that an existing mobile client or a web terminal fails the typing and approval workflow. Language uniformity is less valuable than shipping one useful path.
- **Orchestrator-as-a-sleeve:** Treat this as an optional user workflow, not a core component. Start with explicit CLI dispatch and a simple backlog runner. Giving a quota-driven agent broad hub control before scoped permissions, idempotent jobs, and review boundaries exist is premature.
- **Cross-harness memory:** Cut the proposed `.cstack/` system from the first release. A short, reviewed `HANDOFF.md` in the worktree—goal, state, files changed, tests, next action, and source session IDs—is enough to switch harnesses. Preserve native session history in each harness. Shared transcripts are neither portable memory nor safe instructions.

**A materially lighter architecture:** one host service exposing JSON and a tmux terminal; one CLI using that service; existing WireGuard for phone access; SSH inventory and on-demand remote commands for nodes; Git worktrees for concurrent tasks; optional Linux PID isolation per task; Markdown backlog and handoff files. No resident node agent, Headscale, generated API, Flutter app, or automatic orchestrator initially. The SSH spike already demonstrates the key remote primitive. Add a resident agent only when a measured need arises for disconnected execution or continuously pushed metrics.

**What is missing:** a concrete trust model. “Agents get admin” plus shared live credentials and autonomous backlog dispatch makes the hub a single point of compromise. Specify which identity can invoke which command on which host, how approvals work for family machines, where audit records live beyond the agent’s write access, and how credentials are revoked. Shared writable auth directories also need concurrency testing: two harness processes can race token rotation. For remote jobs, define artifact transfer, cancellation, retry semantics, cache locality, and what happens when a node disappears. Quota readers using undocumented endpoints need a clear “unknown/stale” state so the scheduler never mistakes missing data for spare capacity.
